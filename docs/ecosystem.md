# Papan ecosystem

Papan is one product family with three independently released components: capture links on Android, collect and organize references on desktop, then use saved references in ComfyUI. This page owns the component inventory, shared contracts, compatibility evidence, and tracking conventions. Detailed usage and implementation stay in the linked component documentation.

Release inventory checked on **17 October 2026** against each repository's published GitHub release.

## Components and ownership

| ComfyUI | [chelij/comfyui-papan](https://github.com/chelij/comfyui-papan): saved-board reader, live library adapter, reference node, and workflow persistence | [v0.1.5](https://github.com/chelij/comfyui-papan/releases/tag/v0.1.5) | `VERSION` and `RELEASE_NOTES.md`; [release workflow](https://github.com/chelij/comfyui-papan/blob/main/.github/workflows/release.yml) checks and publishes the versioned ZIP and checksum on a matching tag |

The standalone ComfyUI repository is authoritative. Its frontend has fixes beyond the former embedded copy, and it already owns tests and releases. `extensions/comfyui-papan/README.md` remains only as a migration pointer; desktop no longer builds or publishes an extension. Make extension changes in `chelij/comfyui-papan`. There is no ongoing source mirror.

Version numbers describe each component's own releases. Compatibility follows the shared contracts below, rather than matching component version numbers. ComfyUI reads chosen saved files without requiring a running desktop application. Live connections require desktop v0.3.2 or newer and extension v0.1.4 or newer on the ComfyUI server's computer. Android v0.3.0 has an independent phone library; desktop browsing, session access, previews and nearby recovery require desktop v0.3.3 or newer with a running, reachable receiver and browsing enabled.

## Shared contracts

| Contract | Owner and consumers | Required behavior and reference |
| --- | --- | --- |
| Local phone protocol v1 | Desktop owns the server; Android consumes it | Pairing response version `1`; stable share IDs, durable acceptance and receipts. The mobile-board patch adds opt-in capability discovery, open collection/pin/media browsing, phone-specific password access and optional selected `collectionId`. The reconnection patch adds optional DNS-SD discovery, authenticated identity challenges, phone-initiated requests with explicit desktop approval and interface-address recovery. The thumbnail patch adds optional authenticated `thumbnailUrl`/`variant=thumbnail` video covers, retaining preview/original semantics. The Explore-viewing patch adds optional `X-Papan-Session`/`appSessionAccess` grants and unlocked `preview.{fit,aspectRatio,measuredCount}` metadata; headerless clients retain timed access and locked collections reveal no frame metadata. Pin pages preserve desktop saved/manual order; temporary protection pauses retain unrelated per-collection grants. Existing keys/queues remain v1; preserve legacy QR/default delivery and pending URL/destination identity across retries/restart/revocation. [Protocol and recovery](mobile-sharing.md#local-protocol-v1) |
| Android phone library v1 (Android 0.3.0+) | Android owns its app-private local state | Separate `mobile-library.json` and bounded cached media; atomic link-first saves, collection CRUD, pin edit/search/delete and preview recovery. Unreleased Android source `4e98997` adds native paste/share → media selection → Phone collection → download, running the pinned desktop gallery-dl/yt-dlp/Instaloader worker through Android Python/FFmpeg. Optional v1 `engine`/`items` fields keep selected identities, attachment order and files; legacy `mediaFile`/`kind` cover fields remain, and existing single-media pins can upgrade in place. Provider selections download together using the chosen provider; retries refresh signed source media without switching identities, and atomic failure retains saved files. Storage supports bounded JPEG/PNG/WebP/GIF and MP4/WebM, capped at 32 MiB per selected file. Explicit link-only desktop delivery continues to send the whole original link; no selected-media protocol field or desktop runtime change is introduced. Native viewer actions use one overflow menu, with swipe/keyboard/accessibility navigation and single-line, height-constrained location choices; desktop editing/removal and pose extraction remain desktop-only under existing browse/add consent. Recapture stages separate media until its state commit succeeds, preserving the current preview on failure and reusing an uncommitted candidate across retries. Replaced caches are removed after a successful state commit only when no remaining pin references them. Existing `phone-inbox.json` v1 queues/pairings remain readable. Notebook surfaces, desktop green, single-line preview captions, touching aligned pins, an app-bar collection dropdown and one floating Phone/Desktop/Activity chooser with two alternative menu locations and an upward native reveal are view-only; Phone frames use complete-collection local media proportions and saved local video covers autoplay muted while visible; per-collection preview sizing and theme preferences live separately in phone-only view settings; they do not modify desktop collection settings or wire formats. No desktop `.papan` interchange or implicit synchronization. [Android guide](https://github.com/chelij/papan-android#use-it) |
| Local library protocol v1 (desktop v0.3.2) | Desktop owns the read-only loopback server; ComfyUI v0.1.4's backend adapter and other opt-in adapters consume it | Per-app keys and explicit collection grants; collection/pin/search pages, original/preview byte ranges, and SSE invalidation. Protected collections unlock only in Papan; lock/revoke cancels streams. ComfyUI stores credentials on its server, preserves workflow output identities, and checks live access on every execution. [Setup, protocol and copy limits](app-connections.md) |
| Ordinary `.papan` v1 | Desktop writes; desktop and ComfyUI read | JSON `papan-collection`, version `1`; IDs and referenced media remain meaningful. Recovery backups stay beside their source, including extensionless save names. Absolute media paths must be accessible to the reader. [Saved-file behavior](usage.md#save-lists-or-export-portable-copies), [writer/validator](../src/collection-files.js) |
| Portable `.papan.zip` v1 | Desktop writes; desktop and ComfyUI read | ZIP with `collection.json` (`papan-bundle`, version `1`) and bounded relative `media/` entries; preserve media and reject unsafe paths. [Export/import](../src/portable.js), [archive validation](../worker/archive.py) |
| Encrypted `.papan` v1 | Desktop writes; desktop and ComfyUI read | `PAPANENC` container with authenticated `papan-encrypted` version `1` manifest and media chunks. Preserve password, corruption, and lock handling. [Encryption specification and limits](encryption.md) |
| Saved ComfyUI workflows | ComfyUI extension owns the persisted reader state | Board/item identities, selected output mappings, IMAGE/VIDEO/SECONDS connections, and retained references survive reload without silently rewiring. Imported saved-copy cache fingerprints track changed/deleted files when ComfyUI supplies an empty prompt; live execution still checks current access. [Workflow storage](https://github.com/chelij/comfyui-papan#protected-boards-and-workflow-storage) |

Protection semantics cross these boundaries: phone transport is HTTP on a trusted LAN; desktop encryption protects stored collections; connected ComfyUI references become plaintext input files after unlocking. Preserve these disclosures when changing a contract.

## Tracking and upkeep

1. Search existing issues before creating work. File implementation tasks in the repository that owns the affected code. Include the user-visible result, smallest meaningful check, and relevant contract or version pair.
2. For work crossing repositories, create one coordinating issue in `chelij/papan` with links to component issues and acceptance criteria. Component issues link back. Track status in those issues; add a shared GitHub project when the backlog needs a combined view.
3. When a change affects another component, update this page's contract or compatibility entry and the coordinating issue in the same work. Record exact versions/commits, platform, check, evidence link, and limits. Mark unsupported or untested combinations explicitly.
4. Before publishing a release, check affected consumers and update the intended compatibility and limitations. After publication, update the release inventory with the actual tag/link and checked date. Retain evidence for unchanged behavior; a new tag alone does not establish a new release-pair test.
5. Add future components here before their first release: purpose, canonical repository, contract dependencies, release process, supported compatibility, and evidence. Keep component instructions pointed at this page rather than duplicating the inventory.
